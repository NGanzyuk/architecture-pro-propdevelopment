# Анализ инцидента безопасности Kubernetes

## Исходные данные

Анализ выполнен на основе журнала audit.log кластера Minikube task6. Подозрительные события отобраны скриптом filter-audit.sh и сохранены в audit-extract.json.

## Обнаруженные события

### 1. Попытка доступа к Secret
Пользователь minikube-user, от имени сервисного аккаунта system:serviceaccount:secure-ops:monitoring, попытался получить Secret kube-system/incident-demo-secret посредством операции get. Результатом стала ошибка 403 Forbidden. Подозрительная попытка доступа была пресечена, RBAC заблокировал запрос. Утечки данных не произошло.

### 2. Создание привилегированного Pod
Пользователь minikube-user попытался создать объект secure-ops/privileged-pod с настройкой securityContext.privileged: true. Результатом операции стало успешное создание 201 Created. Исходя из этого можно выделить риск - контейнер получил расширенные полномочия и потенциально может воздействовать на узел.

### 3. Выполнение команды в чужом Pod
Пользователь minikube-user попытался выполнить команду cat /etc/resolv.conf подключившись к контейнеру используя операцию get. API-сервер вернул код 101 Switching Protocols, означающий успешное открытие интерактивного exec-канала. После подключения команда не выполнилась, поскольку в образе CoreDNS отсутствовала утилита cat. Риск - возможность запускать команды в системных Pod.
### 4. Повышение привилегий через RoleBinding
Пользователь minikube-user попытался создал RoleBinding secure-ops/escalate-binding, связав ServiceAccount secure-ops/monitoring с ClusterRole cluster-admin. Результатом явилось успешное проведение операции, а именно код 201 Created. Важно отметить, что создан RoleBinding, а не ClusterRoleBinding. Это означает предоставление прав только на ресурсы внутри secure-ops, а не на весь кластер. 
### 5. Попытка удаления политики аудита
Попытка удаления политики аудита не зафиксирована в журнале Kubernetes. Команда завершилась локальной ошибкой - Git Bash преобразовал путь /etc/kubernetes/audit-policy.yaml в путь файловой системы Windows, поэтому запрос не был отправлен API-серверу. Политика аудита не была удалена. Данный случай показывает, что аудит Kubernetes регистрирует только обращения к API-серверу и не позволяет обнаруживать действия с файлами конфигурации непосредственно на узле.
## Выявленные проблемы безопасности

| Проблема | Подтверждение | Возможные последствия |
|---|---|---|
| Избыточные права пользователя | Создан привилегированный Pod, открыт exec-канал и создан опасный RoleBinding | Компрометация приложений, namespace или узла |
| Отсутствие контроля привилегированных контейнеров | Pod с privileged: true успешно создан | Компрометация узла |
| Возможность повышения привилегий через RBAC | ServiceAccount связан с cluster-admin | Полный контроль ресурсов namespace |
| Ошибка в политике аудита | RBAC-ресурсы указаны в неверной API-группе | Неполные данные для расследования |
| Риск журналирования содержимого Secret | Для Secret задан уровень RequestResponse | Попадание секретов в audit-лог |
| Ограниченная область аудита Kubernetes | Локальная операция с файлом не зарегистрирована | Действия на узле могут остаться незамеченными |

## Рекомендации

| Проблема | Рекомендация |
|---|---|
| Избыточные права | Применить принцип минимальных привилегий |
| Привилегированные Pod | Включить Pod Security Admission restricted |
| Повышение прав через RBAC | Ограничить bind и привязки к cluster-admin |
| Неполный аудит RBAC | Исправить API-группу на rbac.authorization.k8s.io |
| Секреты в audit-логе | Использовать уровень Metadata |
| Действия на узле | Включить аудит ОС и контроль целостности файлов |

## Вывод

Аудит выявил попытку чтения Secret, создание привилегированного Pod, использование exec и повышение прав через RoleBinding. Для снижения рисков необходимо ограничить RBAC-права, запретить привилегированные Pod и доработать аудит.
